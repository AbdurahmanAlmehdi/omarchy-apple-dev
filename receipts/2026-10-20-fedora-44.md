## Fedora 44 (x86_64) — SwiftUI app built, signed, installed and launched on iPhone

Community test report, 2026-10-20. On Fedora 44 x86_64, the repository's **full mode** installer completed with **Swift 6.4.1 (official UBI 9 tarball)** and an **Xcode 27.1 `.xip`**. A simple native SwiftUI app was subsequently **compiled, signed, installed via USB, and launched on a physical iPhone 15 Pro**. Its on-screen button updated a counter successfully.

**Important qualification:** this successful deployment required building **newer upstream xtool separately** and installing a **full (non-slim) Darwin SDK**. The repository's pinned patched xtool built the app but could not complete Apple ID authentication during this test. **LLDB attachment and a modified-source redeploy have not been verified.** This is a community test of a two-stage workaround, not yet proof that the stock installer alone can deploy.

### 1. Install Fedora dependencies

These are Fedora package names, not the Arch or Ubuntu equivalents. This is a consolidated install command for the full-mode toolchain, rather than a minimal dependency set:

```sh
sudo dnf install \
  binutils bzip2-devel ca-certificates cmake curl file \
  gcc-c++ git gnupg2 libstdc++-devel \
  fuse3-devel libcurl-devel libedit-devel \
  libheif libheif-devel libheif-tools \
  libimobiledevice-devel libimobiledevice-utils \
  libxml2-devel libzstd-devel ncurses-libs \
  openssl-devel pkgconf-pkg-config poppler-utils \
  python3 python3-devel python3-pip \
  rsync unzip usbmuxd xz-devel z3-devel zip zlib-devel llvm
```

Several details matter:

- **`fuse3-devel`**, **not** `libfuse3-devel`. Installing FUSE for AppImages does not necessarily install the build headers.
- **`libheif-tools`** supplies `heif-convert`; `libheif` on its own does not. `libheif-devel` supplies development files.
- **`gcc-c++` / `libstdc++-devel`** supply the standard C++ headers; without them, xtool's `zsign` build failed at `#include <string>`.
- **`xz-devel`** supplies `/usr/include/lzma.h`; without it, Swift's `unxip` build repeatedly failed to import its `lzma` C module.
- **`python3-devel`** supplies `/usr/include/python3.14/Python.h` on Fedora 44. Without it, pip failed building the `pylzss` C extension in the installer's `pymobiledevice3` venv.
- **`libimobiledevice-devel` and `openssl-devel`** resolve the installer's `pkg-config` development dependency warning.

Optional checks before running the installer:

```sh
command -v heif-convert
command -v pdftocairo
pkg-config --modversion fuse3 libheif liblzma libimobiledevice-1.0 openssl
ls /usr/include/lzma.h /usr/include/python3.14/Python.h
```

### 2. Install a Swift 6.4.1 toolchain

Use an official [Swift UBI 9 Linux toolchain](https://www.swift.org/install/linux/ubi/9/), **not** Arch's AUR `swift-bin` package. These commands retain the toolchain's `usr/` directory structure so SwiftPM can find its libraries:

```sh
SWIFT_ROOT="$HOME/.local/opt/swift-6.4.1"
mkdir -p "$SWIFT_ROOT"
curl -fL \
  'https://download.swift.org/swift-6.4.1-release/ubi9/swift-6.4.1-RELEASE/swift-6.4.1-RELEASE-ubi9.tar.gz' \
  -o /tmp/swift-6.4.1-ubi9.tar.gz
tar -xzf /tmp/swift-6.4.1-ubi9.tar.gz \
  -C "$SWIFT_ROOT" --strip-components=1
export PATH="$SWIFT_ROOT/usr/bin:$PATH"
swift --version
```

For **Fish** instead of the Bash `export PATH=...` line, run:

```fish
fish_add_path "$HOME/.local/opt/swift-6.4.1/usr/bin"
swift --version
```

Make sure Swift's own `clang` / `clang++` precedes the system Clang. The installer adjusts `PATH` during its operations.

### 3. Run the upstream installer in full mode

Download the matching Xcode `.xip` from [Apple Developer Downloads](https://developer.apple.com/download/all/?q=Xcode), then:

```sh
git clone https://github.com/joshuaswarren/omarchy-apple-dev.git
cd omarchy-apple-dev
env XCODE_XIP="$HOME/apple-dev/Xcode_27.1.xip" \
  ./install-toolchain.sh --mode full
```

Replace the Xcode path with your actual downloaded file. Swift 6.4.x matches Xcode 27.x according to this repo's version table. The first build can take quite a while, as `xtool` and other host tools are compiled from source. The installer is designed to be re-run and reuse its cache.

The `No pacman: skipping the Arch package steps` message is expected on Fedora. The printed Ubuntu Swift download example is generic and does not indicate failure if Swift is already on `PATH`.

### 4. Check the installer's toolchain, then use newer xtool for authentication/deployment

The installer finished with:

```text
== 7. Apple ID sign-in (interactive, needed before device deploys) ==
Run: /home/<user>/.local/bin/xtool auth
Done. Next: plug in the iPhone and run ./device-run.sh
```

The installer pins its own patched xtool fork at commit `f0a1f90efdbb0dc023e276ff529da92618da7a87` and generates a Darwin SDK from the Xcode archive. The patched binary **successfully built the sample SwiftUI app**, but its Apple ID authentication encountered `-80045` in this test. Updating Xcode alone does **not** update this pinned xtool source.

**Verified working upstream commit:** `aa6ba75e7df759a84560885a86822dd119da8c55`

With this revision:
- Apple ID authentication succeeded.
- SwiftUI application compiled successfully.
- USB provisioning, signing, and installation succeeded.
- Application launched successfully on physical iPhone hardware.

```sh
swift --version
swift sdk list  # expected: darwin
"$HOME/.local/bin/xtool" --version
```

To use the newer authentication implementation **without replacing the installer's patched binary**, build upstream separately:

```sh
mkdir -p "$HOME/src"
git clone https://github.com/xtool-org/xtool.git "$HOME/src/xtool-main"
cd "$HOME/src/xtool-main"
git checkout --detach aa6ba75e7df759a84560885a86822dd119da8c55
swift run -c release xtool auth
```

The upstream checkout was able to authenticate on this machine. Its authentication state was **not shared** with the pinned installer version (`~/.local/bin/xtool auth status` still reported logged out). Use the upstream executable explicitly in all subsequent commands:

```sh
XTOOL="$HOME/src/xtool-main/.build/release/xtool"
"$XTOOL" auth status
```

The initial attempt at `"$XTOOL" dev` rejected the previously generated Darwin SDK as **out of date and installed in slim mode**. With the existing Xcode 27.1 archive available, the following command installed the full SDK; **do not add `--slim`**:

```sh
"$XTOOL" sdk install "$HOME/apple-dev/Xcode_27.1.xip"
swift sdk list
```

The full SDK and the repository-generated SDK are not equivalent configurations. Replacing the SDK may require reinstalling repository-specific SDK modifications for more complex apps. **Only the basic SwiftUI sample was checked against the full SDK.** At one point after the SDK switch, authentication appeared logged out; re-authentication restored it, but the cause of the state change was not isolated:

```sh
"$XTOOL" auth status
"$XTOOL" auth  # only if logged out
```

### 5. Physical iPhone smoke test — verified

The test package was a simple SwiftUI counter built in `~/Documents/monkeyhello`. A project-local `xtool.yml` was added to avoid falling back to the `com.example` organization ID:

```yaml
version: 1
bundleID: dev.monkeytools.monkeyhello
```

Use your **own unique bundle ID**. From that Swift package's root, with the iPhone connected over USB and trusted:

```sh
cd "$HOME/Documents/monkeyhello"
"$HOME/src/xtool-main/.build/release/xtool" dev
```

The successful run reported:

```text
Building for debugging...
[3 / 3] monkeyhello-App-product
Build complete! (0.84 secs)
Waiting for device to be connected...
[Unpacking app] 100%
[Preparing device] 100%
[Provisioning] 100%
[Signing] 100%
[Packaging] 100%
[Connecting] 100%
[Installing] 100%
[Verifying] 100%
```

The app was present on the physical iPhone 15 Pro, launched successfully after trusting the developer account in iOS Settings, and updated its visible tap counter. Thus **native SwiftUI build, signing, USB install, launch and basic UI interaction were verified on Fedora 44**.

There was one failed attempt before the success: provisioning returned HTTP 409, `ENTITY_ERROR`, with `There are no current IOS devices on this team matching the provided device IDs.` Running `xtool ds devices list` displayed no devices at that moment. The next attempt succeeded **after adding the explicit `xtool.yml`**. The causal link was *not* established: a delayed device registration or other state change could also explain the retry succeeding. Do not present the bundle ID change as a confirmed fix for this particular 409.

Do not commit Apple Account addresses, team identifiers, pairing records, device UDIDs, certificates, tokens, or raw authentication logs.

### ncurses and LLDB notes

The repo currently warns that UBI 9/10 Swift toolchains on Fedora need `--curses-compat`. **No compatibility shim was manually applied during this Fedora 44 install**, and the installer finished. The stock `ncurses-libs` appeared sufficient for the installation steps; device debugging remains unverified. If an individual system has missing libraries, inspect the actual `ldd` output before applying the optional shim.

The installer's diagnostic still reported:

```text
WARNING: lldb needs libpython3.9.so.1.0; ask an admin for it
```

This was nonfatal for installation. However, running lldb --version and lldb -b -o quit both failed because libpython3.9.so.1.0 could not be loaded. Debugger attachment remains unverified. Fedora 44's default Python 3.14 development headers solve the `pylzss` build; they **do not** solve this unrelated LLDB Python 3.9 ABI dependency. Do not symlink `libpython3.14` to `libpython3.9` as a workaround.
